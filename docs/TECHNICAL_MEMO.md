# Technical memo — Japanese financial tables from PDF pages (1½ pages)

**Question.** Which extraction path should handle which kind of page, and what can be claimed from the evidence we have?
**Scope.** Single pages; 3 real pages (original supplied sample, ELECOM p9, Daiwabo p10) + 15 derived/synthetic controls; CPU only; references are **AI drafts, none human-verified**; OMRON unavailable. Details and every number: `RESULTS.md`.

**System.** One schema (`benchmark-1.0`: exact printed `raw` + typed `value` + explicit `status` + page-coordinate boxes + method provenance), five backends behind it, one evaluator that matches rows/cells without positional assumptions and reports every denominator, a rule-based router, and a local viewer.
Backends: the frozen text-geometry baseline (`v2`); `native_grid` (text-layer clustering: N columns, several tables, grouped headers, three alignments); Docling layout + TableFormer with/without cell matching; Docling + RapidOCR for raster pages. No model was trained; the learned components are pre-trained Docling/RapidOCR checkpoints (revisions pinned in `docs/ENVIRONMENT.md`).

**What the measurements support.**
1. *Clean text-layer pages need no model.* Every text-layer path reproduced all 74 + 56 numeric tokens of the original and ELECOM pages with exact glyphs (`△`, `△0`, `－`). The parsers cost ≈0.17 s cold/≈80 MB; Docling ≈12 s cold/≈1.4 GB for the same tokens and no hierarchy.
2. *Layout complexity, not text quality, is what breaks systems.* On the Daiwabo slide (3 tables, side by side + unruled lower block) the frozen baseline aligns 2/63 cells while still reporting `partial`; Docling with cell matching merges the tables into one grid; without cell matching it returns no text (measured cause: docling-parse emits whole-row text lines and `get_text_in_rect` needs >50 % of a line inside one cell). A geometry-first parser got 63/63 — in-sample. Feeding Docling the table regions fixed the flattening (51/63, no silent loss): the weak link is region detection, not TableFormer.
3. *Raster pages need OCR; native paths fail closed.* Without a text layer all text-layer backends abstain (0 silent omissions). OCR recovers digits without error, but kanji are misread (産→產, 売→壳; 20 of 63 paired rows) and thin `－` placeholders are never detected. We flag rather than repair: variant glyphs (8/11 and 5/9 wrong labels caught, suggestion right every time), ink in empty slots (2/2 dashes, 3 false positives on one page). A bigger OCR model did not help (5× slower).
4. *Routing earns its keep.* The router answered 12 of 13 digital pages from the text layer in 0.2–0.3 s and called models only for raster pages and one arithmetic alarm.
5. *Silent failure is the real risk.* The worst outcomes were not low scores but quiet ones: baseline `partial` with 65/67 cells missing and no omission warning; Docling success-like output under `/Rotate 90` (74/74 cells lost); my own alignment change turned an explicit abstention (`vertical_spacing`) into fragmented labels. The evaluator's silent-omission and false-assurance rates exist to catch this; they depend on the warning vocabulary and are reported with that caveat.

**What it does not support.** Any accuracy claim on unseen layouts or issuers (the best parser was developed on these pages); anything about grouped headers/composition-% on a real page (OMRON missing; only synthetic controls, which also drove the fix); GPU behaviour; scan robustness (rasters are clean renders); any VLM or PaddleOCR-VL result.

**Next steps by value.** (1) A human pass over the review queue (`docs/MANUAL_REVIEW_QUEUE.md`), starting with the 38 sign/dash/plus cells. (2) OMRON p13 and one more unseen issuer, run *before* touching any code. (3) Selective crop re-reading (OCR/VLM only where native and checker disagree) instead of page-wide OCR. (4) Warn on label fragmentation and add an explicit region-detection check so that flattening is reported instead of scored.
